# Klimr — Migrations Ledger (authoritative)

**This file is the single source of truth for what has been applied to the
production Supabase database.** It supersedes `GO_LIVE.md` (deleted Aug 2026 —
its migration instructions stopped at 0022 and were dangerously stale) and the
old `schema_combined_*.sql` snapshots (also deleted).

**How deployment works here (deliberate, recorded decision D5):** every
migration is pasted manually into the Supabase SQL editor by Gabriel, in
order, exactly as delivered in chat with its `-- 0NNN_name.sql —` header. The
Supabase CLI is intentionally **not** part of this workflow until the first
technical hire onboards. Migrations are proven in a scratch Postgres 16
cluster before delivery. Batches flagged **risky** (destructive DDL, data
rewrites, trigger/constraint changes on hot tables) require a proven recovery
path before they run.

**Recovery standard (Aug 2026).** The project has been on the Supabase **Pro**
plan since **Aug 5, 2026**, which runs **daily backups with 7 days of
retention**. Point-in-time recovery is a separate paid add-on and is *not*
included, so the granularity of recovery is "yesterday", not "five minutes ago".

- **Anything that writes, rewrites or drops data** — take a backup immediately
  before the paste (Supabase → Database → Backups), and note the timestamp in
  the row below. With 7-day retention and no PITR, a destructive migration whose
  damage is noticed on day 8 is not recoverable.
- **Grants / policies / views / functions only** — no row is touched, so a backup
  is not the recovery path. These ship with a *tested revert script* instead,
  e.g. `docs/ROLLBACK_0191_0192.sql`, which was applied to a replay of the full
  history and proven to restore the previous behaviour exactly.
- **Storage is not covered.** Supabase's daily backup is the Postgres database.
  Objects in `avatars`, `feed-media`, `credential-docs`, `tournament-payments`
  and the rest are not in it. A database restore would leave every media path in
  the database pointing at bytes that no longer exist. This is exactly the gap
  KCDX-053 names, and it is still open — Pro did not close it.

The app self-checks at boot: `lib/schema-check.ts` probes sentinel columns
and refuses to serve a production deploy against a database that is missing
migrations, pointing back to this ledger.

## Sentinels (keep in step with `lib/schema-check.ts`)

Two layers. Column probes need no database objects and survive an empty manifest; the manifest catches everything a column probe structurally cannot.

| Layer | Covers |
|---|---|
| Column probes | `court_sessions.paused_by / activated_at / display_code` (0124/0127/0128) · `join_requests.offered_at` (0173) · `court_sport_intel.verifying_at` (0175) |
| `schema_manifest_missing()` (0190) | Every app-required table and function from 0176–0189, **plus `service_role` EXECUTE on each function** |
| `profile_boundary_intact()` (0191) | That no table-level SELECT grant on `profiles` has been restored to `anon`/`authenticated` |
| `queue_boundary_intact()` (0192) | That the queue tables stay unreadable, session credentials stay withheld, and presence is not back on the Realtime publication |
| `tournament_boundary_intact()` (0193) | That members cannot write registrations, rosters or payments directly, i.e. the commands are not being bypassed |
| `moderation_reentry_intact()` (0194) | That all three re-moderation triggers are present and enabled |
| `video_disabled_intact()` (0195) | That the video-reject trigger is live and `feed-media` still refuses video MIME types |
| `grant_hygiene_intact()` (0196) | That no member role holds TRUNCATE/REFERENCES/TRIGGER and `anon` reads only the deliberately public tables |
| `media_integrity_intact()` (0199) | That no member-authored write path into a screened bucket has returned, reviewed evidence stays frozen, and every member-facing bucket declares size/MIME limits |
| `enrollment_boundary_intact()` (0201) | That no learner-authored UPDATE policy on enrollments has returned, the session/class FK is structural, and the business guard still covers INSERT |
| `team_ownership_intact()` (0202) | That every roster has exactly one owner, `teams.created_by` agrees with it, and no UPDATE policy on `team_invites` has returned |
| `review_integrity_intact()` (0203) | That the application freeze trigger is live and every decided application carries the hash of what was decided |
| `offer_invariants_intact()` (0204) | That the one-accepted-offer index and the offer identity freeze are live, and no listing has two accepted offers |

**When a migration adds an app-required table or function, add it to the manifest in the same batch.** The manifest is the contract between the deployed code and the database; if it drifts, the sentinel stops meaning anything.

## Reproducibility

`supabase/harness/replay.sh` replays the whole history against a disposable PostgreSQL 17 cluster in two modes — `empty` (clean rebuild) and `upgrade` (0188 absent, 0189 must reconstruct it). Both run in CI on every push. The pass condition is the catalog fingerprint agreeing with production across all fifteen measures, not the row counts; see `introspection/5_catalog_fingerprint.sql` in the remediation bundle and `POST_0189_VERIFICATION.md` for the expected values.

Two facts about production live outside this history and are reproduced by the harness shim rather than by a migration: Supabase's platform default privileges, and the fact that production runs PostgreSQL 17.6.
